# Proposal

## Why

The first automated `v2.0.0` publication stopped before npm because ywtc's release validator only accepted the legacy changelog heading syntax, while Release Please generated its standard linked heading with a parenthesized date. The already-created immutable tag also contains that validator, so an authorized recovery run needs to use the corrected validator from trusted `master` while continuing to package the exact tagged source.

## What Changes

- Accept the dated changelog headings generated by Release Please, while retaining support for the existing legacy heading format.
- Add regression tests for accepted and rejected heading variants.
- Support both npm 11 array and npm 12 keyed-object results from `npm pack --json` in package verification and artifact selection.
- Make manual release recovery validate tagged metadata and package checks with current trusted release-control tooling from `master`, then restore, build, and publish the unchanged tagged revision.
- Preserve idempotent npm, GitHub artifact, release-note, and Homebrew repair behavior.
- Do not move or recreate tags, overwrite npm versions, weaken quality checks, or introduce publication tokens.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `release-management`: Define Release Please-compatible changelog validation and safe recovery of an already-created release tag after publication automation fails.

## Impact

- Affects release validation, npm pack result handling, release workflow recovery, unit tests, and the release-management specification.
- Does not change the ywtc CLI, transfer data model, provider APIs, runtime credentials, or published package contents except for future validator source included in packages.
